# ADR-0007: File storage behind a port: local volume now, blob/S3 later

- **Status:** Accepted
- **Date:** 2026-10-15
- **Deciders:** IntelTPS team

## Context and Problem Statement
The base spec names Blob/Data Lake storage; the hosting decision (PRD §21) is a laptop. Originals (all versions) and generated exports must be stored privately, never lost on processing failure (base spec §5.4), and be movable to object storage later.

## Decision Drivers
- Portability rule (PRD §21); zero cost now
- Restricted downloads, tenant isolation of files
- Path-traversal safety with untrusted filenames

## Considered Options
1. **`StoragePort` with `LocalVolumeStorage` now and an S3/Blob adapter later; files streamed through the API**
2. MinIO container now (S3 API locally)
3. Store files as `bytea` in Postgres

## Decision Outcome
Chosen option: **Option 1**.
- Port: `put(key, stream, content_type) -> StoredObject(key, size, sha256)`, `open(key) -> stream`, `delete(key)`, `exists(key)`.
- Keys are generated by the server: `org/{organisation_id}/docs/{document_id}/v{n}/{uuid}.{ext}` and `org/{organisation_id}/exports/{export_id}.{ext}`. User filenames are metadata only, never path parts. The adapter rejects keys that resolve outside its root.
- Upload order: sniff type and size, stream to storage computing SHA-256, then **one transaction** inserts the document version, usage increment, audit event and `ingest` job. If the transaction fails, delete the file (plus a nightly orphan sweep). Original files are never modified or deleted by processing.
- Downloads and PDF.js viewing go through `GET /api/documents/{id}/file?token=...`. The API checks the HMAC token (ADR-0005) and streams the file with `Content-Disposition` and `X-Content-Type-Options: nosniff`. A future blob adapter may redirect to a provider SAS/presigned URL instead.

### Consequences
- Positive: zero cost, simple backups (named volume + DB dump), swap by config (`STORAGE_BACKEND`, `STORAGE_ROOT`/bucket).
- Negative / Tradeoff: streaming files through FastAPI uses API worker time (fine at < 10 users); the local adapter has no encryption at rest beyond the disk's (enable BitLocker on the laptop); two stores (DB + volume) can drift, so backup and restore must capture both together.
- Follow-ups: backup script dumps Postgres and tars the volume with the same timestamp; restore is tested once (base spec §4.2).

## Pros and Cons of the Options

### Option 1
- Good: simplest, meets portability.
- Bad: no S3 semantics tested until migration.

### Option 2
- Good: exercises the S3 API early.
- Bad: one more container and RAM for no MVP benefit.

### Option 3
- Good: one store, transactional.
- Bad: DB bloat, slow backups, large-object handling in the ORM.
