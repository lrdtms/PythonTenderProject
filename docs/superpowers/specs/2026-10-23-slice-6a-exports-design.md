# Slice 6a: Exports (design)

**Date:** 2026-10-23 · **Branch:** `feat/slice-6a-exports` (based on `feat/slice-5b-estimate`) · **Status:** draft for owner review. Calls marked **(my call)** are the author's choices, not agreed with the owner.
**Authority:** `docs/plan.md` section 3 (Slice 6 row: "Export approved estimate"), `docs/prd.md` FR-38 (Excel), FR-39 (PDF checklist report), FR-62 (status and version on exports), section 8 (Estimates / Exports data model), section 9 (exports API), section 10 step 8 ("Export approved items only. Draft exports are clearly labelled"), architecture sections 2, 4.1 and 9 (reporting module, fitness function F11: Excel export of 1,000 lines in under 10 s, module boundaries), ADR-0007 (storage port), the 5b spec (the frozen estimate), `docs/dependency-audit.md`. Frontend rules: `frontend/AGENTS.md`.

5b ends with an approved, frozen estimate and no file. 6a turns an estimate version into an Excel workbook and a tender's requirements into a PDF checklist report, stores each file through the storage port, records it in an `exports` table, and serves it back through an authenticated same-origin download. Slice 6 is split: **6a is exports only**. The audit view, usage limits, start-demo script, backup/restore and the tunnel script are **6b** (section 12) and are not planned here.

## 1. Goal and scope

An estimator on the estimate page presses "Download Excel" and receives a workbook that a reader can trust without opening the app: what tender, which version, which status, who approved it, every line with its supplier, quantity, rates, markup, VAT and total, and the totals, all equal to the numbers on screen to the cent. A PDF of the tender's requirement checklist, grouped by type, shows mandatory status, review status and the source document and page. Anything that is not approved says DRAFT in places a reader cannot miss.

**Exit gate (real Docker stack through Caddy, the synthetic pack used for the 5b gate):**

1. On an approved estimate version, "Download Excel" returns an `.xlsx` whose Summary and Lines sheets match the screen to the cent (totals, each line total, counts), with no DRAFT marking and a filename without a DRAFT suffix.
2. On a draft or reviewed version, the same button produces a workbook marked DRAFT in the banner row of both sheets, in the print header, in the Summary status cell, in the document title and in the filename; the page says before the click that the file will be marked DRAFT.
3. "Download PDF report" on the checklist page downloads a PDF (always served as an attachment, D14) that opens in a PDF viewer, with requirements grouped by type, mandatory flag, review status, source document and page; with unreviewed rows present it is marked DRAFT and lists them in their own section; the page says so before the click even when a filter hides the unreviewed rows.
4. A BoQ description or supplier name starting with `=`, `+`, `-` or `@` (for example `=HYPERLINK("http://x","click")`) opens as inert text in Excel, and a requirement containing `<img src="file:///etc/passwd"/>` shows as literal text in the PDF.
5. A reviewer gets 403 on create and on download; another organisation gets 404 on every export route; an export created before an estimate edit still downloads the same bytes afterwards.
6. F1 green for the new routes; F3, F2 (import-linter) and the `openapi.json` drift check green; the F11 smoke (1,000 lines, under 10 s) green; backend and frontend CI green; `pip-audit` clean with the new dependency.

## 2. Goals, non-goals, anti-goals

**Goals:** one number, one source: every figure in the workbook is a stored or `calc.py` result, never recomputed differently; a file that cannot execute anything when opened; draft output that cannot be mistaken for approved output; every export recorded, owned by an organisation, and audited.

**Non-goals (6a):** CSV or Word export; PDF of the estimate; Excel of the checklist; emailing a file; export history list and delete; scheduled or bulk exports; section subtotals (cut in 5b; the Lines sheet has an auto-filter on the Section column instead); multi-language output; custom templates or logo upload; digital signatures; Excel formulas; signed or shareable links; anything in section 12.

**Anti-goals (failure even if it technically works):** an unapproved estimate that looks approved in the file; a total in the file that differs by a cent from the screen; a cell that Excel evaluates as a formula; document text interpreted as PDF markup; a download that works across organisations or without a session; a float anywhere on the money path.

## 3. Decisions

| # | Decision | Choice and reason |
|---|---|---|
| D1 | Draft versus approved (PRD says "approved only" and "draft exports are clearly labelled") | **Ruling (owner, 2026-10-23): any version may be exported; only an approved version is unmarked.** PRD section 8 says "Draft exports are clearly labelled", which only makes sense if drafts can be exported, so the "approved only" wording elsewhere is amended (Task 1 updates `docs/prd.md` and `docs/architecture/architecture.md`). Refusing drafts would push estimators to screenshot or retype the numbers, which is worse. A non-approved export carries a `label` (`draft` or `reviewed`, the FR-62 statuses) and shows DRAFT in: a red banner row at the top of every sheet ("DRAFT: version N is not approved. Do not submit."), the print header (large red bold, built from fixed codes plus `xlsx_header_text`, D11) on every printed page, the Summary status cell, the workbook title property, the sheet tab colour, and the filename suffix `-DRAFT`. For the PDF, DRAFT is a diagonal watermark on every page plus a header line. |
| D2 | Which estimate version | `estimate_id` is optional in the request. Given: that version (404 if it is not this tender's). Omitted: the highest approved version, else the newest version (labelled), else 409 `no_estimate`. The page always sends the version it is showing, so the file matches the screen |
| D3 | Label values | `exports.label` is one of `draft`, `reviewed`, `approved` (the FR-62 vocabulary; no other value exists). Estimates use the estimate's status. The checklist has no approval step and no version, so its report takes `approved` when every non-rejected requirement is `confirmed` or `corrected` (reviewed by a person) and at least one exists, otherwise `draft`; it is never `reviewed`. The PDF prints no "FINAL" or "APPROVED" word: it is simply unmarked, and the PRD note added in Task 1 says what `approved` means for a checklist |
| D4 | Checklist content (PRD: approved items only) | Confirmed and corrected requirements appear in the main body, grouped by type. Unreviewed requirements appear in a separate last section "Not yet reviewed" and force the DRAFT label. Rejected requirements are left out and counted in the summary ("N rejected, not listed"). Only current document versions are used, like the checklist page. Corrected values are shown (the DTO already holds them); the evidence quote is not printed (it is document text, long, and the source column points at it) |
| D5 | Permission | The existing `Permission.EXPORT` (admin, estimator, project manager; not reviewer) guards create and download. `GET /exports/{id}` (metadata only) needs `READ`. No new permission, no migration of roles, no change to the role matrix. A reviewer therefore cannot download; recorded as a known limitation, and it is a one-line change if the owner wants reviewers to download approved files |
| D6 | Sync or queued | **Synchronous, inside the request.** F11 requires 1,000 lines in under 10 s. openpyxl writes about 21,000 cells in well under a second and ReportLab lays out a few hundred rows in a second or two; the 10 s budget is spent mostly on reading rows. The single worker (concurrency 1) is routinely busy for 90 to 290 s on an extraction job, so a queued export would wait behind it and fail the "click, get file" experience. The cost of sync is a held request and a held DB transaction for about a second. Controls: hard row caps (5,000 lines, 5,000 requirements; above that 422 `export_too_large`), a per-user rate limit (the existing in-memory limiter, 10 per minute), and a perf test against the budget. `GET /exports/{id}` exists for the PRD contract and for a future async mode; a row exists only after its file is stored, so there is no `pending` or `failed` state to model. Revisit if exports ever exceed the caps or take over 5 s in the gate. **(my call)** |
| D7 | PDF library | **ReportLab 5.1.0.** WeasyPrint needs Pango, Cairo and GDK-Pixbuf system packages, which would change the Dockerfile's apt layer, enlarge the image and add native-library CVE surface; it also renders HTML, which invites the markup-injection problem we want to avoid. ReportLab is BSD-licensed, pure Python with a Pillow dependency that is already locked (13.0.0), and needs no system package, so it runs in the existing image unchanged. Checked 2026-10-23: `uv pip compile` resolves `reportlab==5.1.0` against `pillow==13.0.0` plus the already-locked `charset-normalizer`, and `pip-audit` reports no known vulnerabilities on that set. PyMuPDF (already a dependency) was rejected: its layout API is low-level, and its licence (AGPL) is better not extended to new features |
| D8 | Excel library | openpyxl (already a dependency, `>=3.1.5`, locked 3.1.5). No new dependency for Excel |
| D9 | Where orchestration lives | As in 5b: the `reporting` module imports no other module except `audit` (and `kernel`, `db`). The router reads the estimate, tender, member names, requirements and document titles through the other modules' public APIs and maps them to plain input dataclasses (`EstimateExportInput`, `ChecklistExportInput`). The renderers (`xlsx.py`, `pdf.py`) are pure functions of those inputs: no database, no storage, no clock (the timestamp is an input). This deviates from the architecture sketch `create_export(ctx, tender_id, kind)`, whose signature gains the storage port and the payload; architecture.md is updated in the final task. Import-linter gets a contract that isolates `reporting` and a contract that keeps the renderers free of sqlalchemy and fastapi |
| D10 | Numbers | Every amount is written as a numeric cell from a `Decimal` taken from the stored line or the stored/ live totals, with a number format (`#,##0.00` for amounts, `#,##0.0000` for quantities and rates, `0.00` for percentages). **No Excel formulas anywhere**, so the workbook cannot disagree with `calc.py` and nothing is recalculated in Excel's binary floating point. **openpyxl does not write a `Decimal` exactly:** its writer formats every number with `"%.16g"` of a float (verified on the repo's openpyxl 3.1.5: `Decimal("8.174")` is stored as `8.173999999999999`, `91356.93` as `91356.92999999999`, `9735177631648.39` as `9735177631648.391`, `12345678901234.5678` as `12345678901234.57`; about 6% of random 2-decimal amounts differ in the last XML digit). Excel loads that same double and shows 15 significant digits, so the **normative rule** is: a value is written as a numeric cell only if it has at most 15 significant digits, counted on `value.normalize()` (trailing zeros do not count, so `10.5000` is 3 digits); then the double Excel loads, displayed with 15 significant digits, equals the `Decimal` exactly. A value with more than 15 significant digits is written as an inline text cell and the Summary says "Some values have more than 15 digits and are shown as text." Tests therefore assert `Decimal(format(float(raw_v), ".15g")) == expected` for numeric cells, never `Decimal(raw_v) == expected`. The summary figures for a draft are the live computed totals from the estimate DTO; for a frozen version they are the stored totals; neither is recomputed in `reporting`. **(my call)** |
| D11 | Formula injection | One function, `reporting.safe_text.xlsx_text(value)`, is the only way a string reaches an Excel cell. It removes characters XML cannot hold (the control characters that make openpyxl raise `IllegalCharacterError`), truncates to `limit - 4` characters (adding `...`) so the result including the prefix never exceeds `limit` (32,000), and then, on the cleaned text, if the text (after leading space, tab, CR or LF) starts with `=`, `+`, `-`, `@` it prefixes a single quote `'` (the OWASP rule). It also forces the cell's data type to string (`cell.data_type = "s"`, verified: openpyxl then writes an inline string, not `<f>`). Both layers are tested, so the data type alone is not trusted if the file is later saved as CSV. Numbers are never produced from strings. No hyperlink cells are created. Datetimes are never given to openpyxl as aware datetimes (it raises `TypeError`): they are written as text `YYYY-MM-DD HH:MM UTC` through this function, and the workbook `properties` get naive UTC values. Print headers and footers are a separate control language (`&` starts a code, `&&` is a literal ampersand, Excel rejects more than 255 characters per section): they go through `xlsx_header_text(value, limit=60)`, which strips control characters, doubles `&` and truncates, and are assembled from fixed codes plus that output, each section kept under 255 characters. Every user-controlled string goes through one of the two: descriptions, section and item numbers, supplier names, exclude reasons, tender title, reference, client, member names. A visible leading `'` on a description such as "- 2.5mm cable" is the accepted cost |
| D12 | PDF text safety | ReportLab `Paragraph` parses a mini-markup language (`<img src=...>`, `<a href>`, `<font>`), and an `<img>` can read a local file or a URL. Every user string placed in a `Paragraph` passes `reporting.safe_text.pdf_text(value)`, which escapes `&`, `<`, `>`, strips control characters, truncates (to 2,000 characters, appending "... (truncated, see source)" so a cut is never silent; the cap also keeps one table row shorter than the A4 frame), and replaces characters the built-in Helvetica cannot draw (outside WinAnsi) with `?`. Text drawn directly on the canvas (footer, watermark, document title and author metadata) is not markup, so it passes `pdf_plain(value)` (same stripping, truncation and `?` replacement, no escaping) and "Smith & Sons" prints correctly. Tests prove an `<img>`, a `<font color>` and an `&amp;` in a requirement render literally. Embedded TrueType is not used in 6a, so a Zulu or Afrikaans accented letter in WinAnsi prints, while for example `≤` prints as `?` (known limitation; adding DejaVu through the Dockerfile is the follow-up) |
| D13 | Storage | Through `StoragePort` (ADR-0007), key `org/{organisation_id}/tenders/{tender_id}/exports/{export_id}.{xlsx\|pdf}`, server-built, written before the row commits and deleted on rollback. The documents module's private `_delete_on_rollback` becomes a shared helper in `app/db/stored_files.py` (it needs only the `StoragePort` protocol and a session) and both modules use it. The client never supplies a key or a filename |
| D14 | Download | `GET /exports/{id}/download`: session cookie plus tenant check on every request (the same pattern as `/document-versions/{id}/file`, ADR-0007 notes), `Permission.EXPORT`, `StreamingResponse` with the stored content type, `Content-Disposition: attachment; filename="<ascii name>"`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`, `Content-Security-Policy: sandbox`, `Content-Length` from the stored size. The filename is built by the server from the tender title (ASCII letters, digits and hyphens only, at most 40 characters, `tender` when empty), kind, version, `-DRAFT` when not approved, and the UTC date, for example `greenvale-hall-estimate-v2-DRAFT-20261023.xlsx`. It is stored in `exports.file_name`; the user's text never reaches a header unfiltered. Always `attachment`, even for PDF, so the browser saves it and the export cannot be framed |
| D15 | Archived tenders | Exports are allowed on an archived tender (a read of existing data; archived tenders are exactly the ones people file away). They do not take the archived refusal |
| D16 | Consistency | Only an approved estimate is frozen; a reviewed one can be reopened (it goes back to draft, its stored totals are cleared and its lines become editable). So **every non-approved export takes the tender lock first** (`suppliers.lock_tender`, the lock every 5b write takes), then reads the status, then chooses live or empty `LiveInputs` from that status, then reads the estimate and its lines in **one call** (`estimates.export_snapshot(session, ctx, estimate_id, live) -> tuple[EstimateDTO, list[EstimateLineDTO]]`, built on a single `_lines_of` pass), so totals and lines come from the same rows. An approved version needs no lock. The checklist export takes no lock: review writes lock per document version, and a concurrent review edit can land between two page reads. The PDF states its generated time and the counts it saw; recorded as a known limitation |
| D17 | Audit | `export_created` (entity `export`; metadata `kind`, `estimate_id`, `version`, `status` = the label, `count` = lines or requirements) and `export_downloaded` (`kind`). All keys are already in the audit allowlist; no tender title, filename, description or amount is recorded. The download audit row is written in the request transaction before the stream starts |
| D18 | Repeat exports | Every POST makes a new row and a new file; nothing is de-duplicated or overwritten, so a reader who holds an old file can always ask "which export was that" (the export id is printed in the Summary sheet and the PDF footer). Disk growth is bounded by the rate limit and measured in kilobytes per file; retention is a 6b/ops matter and is listed under known limitations |
| D19 | Sheets | Exactly two: `Summary` and `Lines` (section 5). The `Lines` columns are fixed and documented in the golden file so a change is deliberate |
| D20 | Time | `generated_at` is `datetime.now(UTC)` set once in the service and passed to the renderers; files print it as `YYYY-MM-DD HH:MM UTC`. South African users read UTC+2: stated in the file |

## 4. Module placement and data model

**`reporting` module** (the existing stub package):

| File | Responsibility |
|---|---|
| `models.py` | `Export` ORM model |
| `repo.py` | `ExportRepo` (tenant-scoped `get`, `add`) |
| `schemas.py` | `ExportCreate` (request), `ExportDTO`, and the plain input dataclasses `ExportLine`, `EstimateExportInput`, `ChecklistRow`, `ChecklistExportInput` |
| `safe_text.py` | `xlsx_text`, `pdf_text`, `export_filename`; the only place that touches user strings on the way out |
| `words.py` | Plain-words text for line flags, markup basis, VAT basis, review and mandatory status (the backend copy of the vocabulary in `frontend/src/lib/estimate-words.ts`) |
| `xlsx.py` | `render_estimate_xlsx(EstimateExportInput) -> bytes` |
| `pdf.py` | `render_checklist_pdf(ChecklistExportInput) -> bytes` |
| `service.py` | `create_export`, `get_export`, `open_export_file`, label rules, audit, storage |
| `public.py` | The module's surface |

**Foreign keys.** `exports` is an organisation-owned table with composite foreign keys, which F3 checks: `(organisation_id, tender_id)` to `tenders`, `(organisation_id, estimate_id)` to `estimates` (estimates are never deleted, so a real foreign key is safe and keeps an export pointed at its version), and `(organisation_id, generated_by)` to `memberships`.

Migration `0007_exports`:

- `exports`: `id`, `organisation_id`, `tender_id`, `kind` (`estimate_xlsx` or `checklist_pdf`), `estimate_id` (nullable), `estimate_version` (nullable int, a snapshot so the number survives any future version cleanup), `label` (`draft`, `reviewed`, `approved`), `file_key`, `file_name`, `content_type`, `file_size`, `sha256` (64 hex), `row_count` (lines or requirements), `generated_by`, `generated_at` (NOT NULL, no server default: the service stores the very value printed in the file). CHECK constraints for `kind`, `label`, `(kind = 'estimate_xlsx' AND estimate_id IS NOT NULL AND estimate_version IS NOT NULL) OR (kind = 'checklist_pdf' AND estimate_id IS NULL AND estimate_version IS NULL)`, and a checklist row's label is `draft` or `approved`. The composite FK does not tie the estimate to `tender_id`; the service asserts that the estimate's tender equals `tender_id`. Index on `(organisation_id, tender_id, generated_at)`. Unique `(organisation_id, id)`.

**Public API (reporting):** `create_export(session, ctx, storage, tender_id, kind, payload, estimate_id=None) -> ExportDTO` (requires `EXPORT`; the payload type must match the kind; refuses `export_too_large`), `get_export(session, ctx, export_id) -> ExportDTO` (`READ`), `open_export_file(session, ctx, storage, export_id) -> tuple[ExportDTO, BinaryIO]` (`EXPORT`, audits the download).

## 5. Contents of the files

### Excel (`estimate_xlsx`)

**Summary sheet**, two columns (label, value), in this order: DRAFT banner row (non-approved only, merged across, red fill, white bold); title "Tender estimate"; Tender, Reference, Client; Estimate version; Status in words ("Approved", "Reviewed: not yet approved", "Draft"); Approved by and at (or "Not approved"); Reviewed by and at (or "Not reviewed"); Currency; VAT rate (%); Markup basis in words ("Percentage on cost" or "Percentage on selling price"); Default markup (%); Lines priced, excluded, not priced, changed; Subtotal cost, Markup, Subtotal ex VAT, VAT, **Total incl VAT**; for an incomplete estimate a row "Incomplete: excludes N lines" beside the total; Generated by, Generated at (UTC), Export reference (the export id); a note "Amounts are values, not formulas. Quotes that include VAT are converted to ex VAT on the stated rate; nothing is converted between currencies".

**Lines sheet**, a banner row (non-approved only), a header row, then one row per estimate line in BoQ order. Columns: Line, Section, Item no, Description, Unit, Quantity, Supplier, Price source ("Supplier quote", "Manual price", "Excluded", "Not priced"), Quoted unit price, Quote currency, Quote VAT basis ("Includes VAT", "Excludes VAT", "Not stated"), Unit price ex VAT, Labour rate, Material cost, Labour cost, Cost, Markup (%), Markup, Line total (ex VAT), Status ("Priced", "Excluded", "Not priced", "Source changed"), Notes (exclude reason, or the line's flags in plain words). Excluded lines are listed, with their reason, a grey fill and no amounts; unresolved and changed lines are listed with amounts empty and are not in the totals. The effective markup percentage is the line override if present, else the estimate default (a selection, not arithmetic). The header row is frozen, the header is repeated on printed pages, the columns carry an auto-filter, widths are set, the page is landscape and fit to one page wide.

For a frozen version the lines come from `estimate_lines` as stored; for a draft they come from the same DTO the estimate page uses, with the live inputs, so "Source changed" is reported honestly.

### PDF (`checklist_pdf`)

A4. First page: title "Requirements checklist", tender title, reference, client, closing date, generated by and at, label, the export id, and a count table (types by mandatory status, plus "not yet reviewed" and "rejected, not listed"). Then one section per requirement type in the fixed order of `REQUIREMENT_TYPES` that has rows, each a table with repeated header: Mandatory ("MANDATORY", "Conditional", "Information only"), Requirement, Review ("Confirmed", "Corrected"), Source ("<document title>, page N", "page not recorded", or "(source not verified)" when the evidence status is not `verified`). Rows are ordered by document (the order of the tender's document list), then source order, then position; the router sorts them, because the repository orders across versions by source order alone. A last section "Not yet reviewed" holds the unreviewed rows in the same layout. Footer on every page: tender title, "Page X of Y", export id. DRAFT: diagonal light-red watermark and a red header line on every page.

## 6. API

Flat under `/api/v1`, like the rest. Consistent error format.

| Endpoint | Does |
|---|---|
| `POST /tenders/{tender_id}/exports` | Body `{kind, estimate_id?}` (`extra="forbid"`; `estimate_id` only valid for `estimate_xlsx`, else 422). Needs `EXPORT`. Generates, stores, records, audits, returns `201` with the `ExportDTO`. Errors: 404 (tender or estimate not in this organisation), 409 `no_estimate`, 422 `export_too_large`, 429 rate limited |
| `GET /exports/{export_id}` | `ExportDTO`: id, tender_id, kind, estimate_id, estimate_version, label, file_name, content_type, file_size, row_count, generated_by, generated_by_name, generated_at. `READ`. 404 across organisations |
| `GET /exports/{export_id}/download` | The file, per D14. `EXPORT`. 404 across organisations or when the stored file is missing |

A new export does not need a lock beyond D16. No other route changes. `openapi.json` and the generated frontend types change (drift check).

## 7. Frontend

- `frontend/src/api/exports.ts`: `useCreateExport(tenderId)` (POST, JSON with the CSRF header like every write) and `exportDownloadPath(id)` (`/api/v1/exports/{id}/download`). The type is the generated `ExportDTO`. After success the button shows the returned `label` ("Downloaded <name> (marked DRAFT)") and invalidates the estimates queries, so wording that went stale in another tab is corrected by the server's answer.
- `frontend/src/lib/export-words.ts`: plain-words messages for `no_estimate` ("This tender has no estimate yet. Create one first."), `export_too_large` ("This is too large to export in one file."), 403 ("Your role cannot export files."), 429 ("You are exporting too quickly. Wait a minute and try again."), 404, network and a generic fallback.
- `frontend/src/components/export-button.tsx`: one button component for both pages (`kind`, `estimateId?`, `label`, `draftNote?`). On click it creates the export, then starts the download by a programmatic click on an anchor to the download path (same origin, the session cookie authenticates, no file is held in JavaScript memory), and shows "Downloaded <file name>" with the same link as a fallback if the browser blocked the automatic download. While running it is disabled and says "Preparing file". Hidden without the `export` permission (`useCan("export")`; the API still enforces).
- Estimate page: "Download Excel" beside the version picker for the version being shown. When that version is not approved the label reads "Download Excel (DRAFT)" and a line says "This file will be marked DRAFT because version N is not approved." No button on a tender with no estimate.
- Checklist page: "Download PDF report". When unreviewed requirements exist, a line says "N requirements are not reviewed yet. The report will list them separately and be marked DRAFT."
- Keyboard operable; status text is words, never colour alone; types from the regenerated `openapi.json`.

## 8. Testing

- **Golden file, Excel:** a committed JSON of every cell value (and number format) of both sheets for a fixed three-section estimate with a supplier line, a VAT-inclusive quote line, a manual line, an excluded line, an unresolved line and a labour and markup-override line; read back with openpyxl and compared cell by cell, amounts as `Decimal` from the XML value (not through a float). The generated-at and export id inputs are fixed.
- **Draft label:** draft and reviewed inputs produce the banner on both sheets, the print header, the status cell, the title property, the tab colour; an approved input produces none of them; the filename suffix follows. Header and footer corpus (`A & B`, `&Z&F`, `&"Arial,Bold"x`, a 300-character title): the footer XML holds the escaped form and every header and footer section is under 255 characters.
- **Formula injection:** a corpus (`=1+1`, `+SUM(A1)`, `-2+3`, `@SUM(1)`, `\t=1`, ` =1`, `=HYPERLINK("http://x")`, a 40,000-character string, control characters, `<script>`) in every user-text field; assert no cell has data type `f`, the stored text starts with `'` where needed, nothing raises, and the sheet XML contains no `<f>` element and no hyperlink part.
- **Precision:** `8.174`, `91356.93` and `9735177631648.39` (stored by openpyxl as `8.173999999999999`, `91356.92999999999`, `9735177631648.391`) must display as themselves at 15 significant digits; `10.5000` counts as 3 digits; values with 16 or more normalised digits are inline text cells and the Summary notes it. Assertions use `Decimal(format(float(raw_v), ".15g"))`, not exact XML equality.
- **PDF smoke:** the bytes start with `%PDF`; pdfplumber or PyMuPDF opens it; expected text is present (tender title, each type heading, mandatory word, a document title and page); DRAFT text present when draft and absent when the label is `approved`; `<img src="file:///...">`, `<font color=red>` and `&amp;` appear literally; a 5,000-character requirement does not crash layout; an empty checklist renders a clear message; page count and "Page X of Y" are right.
- **Service and store:** create writes the file and the row, audits with safe metadata only, and an induced failure after `put` deletes the file; checks constraints; F3 passes for `exports`.
- **API:** per role (reviewer 403 on create and download; estimator, project manager, admin 201); default version rules (D2); `estimate_id` of another tender or organisation is 404; no estimate is 409; download headers (type, disposition, nosniff, no-store, sandbox, length); download of a missing file is 404; archived tender export works; draft export reflects live "source changed"; frozen behaviour: export, edit the BoQ and a quotation, export again from the same approved version, the two workbooks are identical in every cell except "Generated at" and "Export reference" (excluded deliberately and named in the test), and the Lines sheet is identical in full; an approved export and a later new draft do not interact.

## 10. Risks

- **A cent of difference between screen and file:** the worst failure for a pricing tool. Mitigation: no formulas, values copied from the same DTO, golden file, `Decimal`-exact XML comparison.
- **Draft mistaken for approved:** mitigated by five separate markings in the workbook and by the pre-click wording; tested for presence and for absence on approved.
- **Injection (Excel formula, PDF markup, header):** one funnel function per format, a corpus test, and a server-built filename.
- **Sync generation blocks a request thread:** bounded by caps and a rate limit; measured by the smoke test; fallback is the jobs queue (the table already fits it).
- **Draft export reads many rows:** the 5b estimate page already "reads all quotation items on each request" (known limitation), so a draft export of a large tender is the slow path, not the render. The F11 smoke measures the frozen path; the draft path is timed in the gate and its number recorded. If it passes the budget, the lines come from the DTO without candidates (not needed by the file).
- **New dependency:** ReportLab. It is pinned in `uv.lock` and the CI audit step covers it (section D7). Its parser is the injection surface, hence D12.
- **Disk growth:** one file per click. Rate limited; retention deferred.

## 11. Known limitations this slice will add

- A reviewer cannot download (D5).
- A programmatic download of an error response (expired session, deleted file) saves the JSON error body under the file name; the page shows the plain-words result of the create call, and the download itself is not probed first.
- The download is an audited GET under a SameSite=Lax cookie: a cross-site top-level link can add `export_downloaded` rows for a logged-in user; nothing leaks, the file goes to the user's own browser.
- The PDF uses the built-in Helvetica: characters outside WinAnsi print as `?`.
- The checklist PDF does not print the evidence quote.
- The checklist export reads without a lock, so a review edit landing during the read may be half-included; the file shows its generated time and counts.
- Timestamps in files are UTC.
- No export history list, no delete, no retention; every click keeps a file.
- No section subtotals in the workbook; the Lines sheet has a Section filter.
- A description beginning with `=`, `+`, `-` or `@` shows a leading apostrophe in Excel.
- Values beyond 15 significant digits are text in the workbook.
- The workbook has not been opened in every spreadsheet application; the gate opens it in Excel if available and otherwise records that it was checked by reading the XML only.
