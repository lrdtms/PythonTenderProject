# Slice 6b: Audit view, usage limits and operations (design)

**Date:** 2026-10-23 · **Branch:** `feat/slice-6b-operations` (from `main` after PR #8) · **Status:** written without an interview at the owner's request ("just write the spec and plan, then execute it"). Every choice below is the author's call (marked **(my call)** where it is a real fork) and is recorded as a decision, not as something agreed.
**Authority:** `docs/plan.md` section 3 (Slice 6 row: "audit view, usage limits, start-demo script, backup/restore, tunnel"; exit gate "restore tested; demo starts with one command"), `docs/prd.md` FR-47 to FR-50 (plans, usage, mocked billing), section 5 note on mocked billing, section 8 ("Plans / Usage"), section 9 (`GET /usage`), section 10 (security, audit), section 21 (tunnel, marking-window checklist, operations), the 6a spec section 12 (what 6a deferred), ADR-0009 (single origin), `docs/known-limitations.md`.

6a ended with exports. 6b is what makes the system safe to run on a laptop in front of markers: someone can see what happened (audit), a runaway account cannot exhaust the machine (usage limits), the stack starts with one command, the data can be backed up and a restore has been proven, and the public link is created and checked by a script.

## 1. Goal and exit gate

**Exit gate (real Docker stack through Caddy; ops scripts run for real; anything not run is listed under "Not covered"):**

1. **Audit.** An admin and a project manager open "Audit" and see this organisation's events newest first with who did it (name), what, on which kind of object, when, and the safe metadata; they filter by action, object kind, person and date range and page through with "Load more". An estimator and a reviewer get 403 from the API and no Audit link. Another organisation's events never appear.
2. **Usage.** Any member sees plan, limits and current usage on the Usage page. On the small plan, the (limit+1)th tender, upload, export or member is refused with 403 `limit_exceeded` and a message that names the resource and the limit; nothing was created; usage and the refusal reason are visible on the page. An admin can switch the organisation between the two seeded plans (mock upgrade), audited. No payment code exists.
3. **Status.** `/status` (no login) shows API, database and model reachability in plain words; it leaks no version, host or path.
4. **One command.** `scripts/ops/start-demo.ps1` on a machine with Docker and Ollama: refuses to run with unsafe config (default `SECRET_KEY`, `COOKIE_SECURE=false` or `ENVIRONMENT` not `production` when `-Tunnel` is used), checks Docker and the model, preloads the model, builds and starts the stack, waits for health, optionally opens the tunnel, and prints the local and public URLs and the marking-window checklist.
5. **Backup and restore.** `backup.ps1` writes a directory with a database dump, a files archive and a manifest (checksums, row counts, migration head). `restore.ps1 -Verify` restores into scratch space and proves counts and checksums match the manifest without touching live data. `restore.ps1 -Apply`, run against a second, empty Compose project, brings the stack up with the same tenders, users and files (login works, a stored document downloads, row counts equal the manifest).
6. **Tunnel.** `tunnel.ps1` starts `cloudflared`, reads the public URL, checks `https://<url>/api/v1/health`, and records the URL; `-Stop` ends it. If `cloudflared` is not installed in the gate environment, items for it are reported "not run", not passed.
7. F1 (new routes), F2, F3 (new tables), role matrix, `openapi.json` drift, ruff, lint-imports, pip-audit, backend pytest, frontend lint/typecheck/build/vitest all green.

## 2. Goals, non-goals, anti-goals

**Goals:** an audit trail a project manager can read without help; limits that are real (enforced server-side, race-safe, tenant-scoped) and honest (the page says what is used); an ops path a tired person can run in the marking window; a restore that has actually been run.

**Non-goals (6b):** payment, invoices, plan editing UI beyond switching between the seeded plans; per-user quotas; usage history charts; audit export, delete or retention jobs; audit of read access; alerting; a platform-admin role; Linux/macOS scripts (the target machine is Windows, PowerShell 7); scheduled backups (run by hand or Task Scheduler, documented); off-machine backup copy (documented, user-managed); seeding demo accounts; an export history list.

**Anti-goals:** a limit that can be passed by two concurrent requests; a limit check that counts another organisation's rows; an audit page that shows a column the allowlist does not permit or renders metadata as HTML; a "restore tested" claim without the manifest comparison; a start script that opens the tunnel with a default secret; a backup that silently omits the files volume; a restore `-Apply` that can hit the live project by accident.

## 3. Decisions

| # | Decision | Choice and reason |
|---|---|---|
| D1 | Audit read API | `GET /api/v1/audit`, `Permission.VIEW_AUDIT` (admin and project manager already hold it; no matrix change). Query: `entity_type`, `action`, `user_id`, `from`, `to` (ISO dates, UTC, inclusive), `cursor`, `limit` (default 50, max 100). Keyset paging on `(created_at, id)` descending, cursor is an opaque base64 of the last pair; no offset. Only rows of the caller's organisation (events with null organisation are never returned). `GET /api/v1/audit/facets` returns the distinct `entity_types` and `actions` seen in the organisation, for the filter dropdowns. The existing index `ix_audit_events_org_created` serves the query |
| D2 | Audit response | Items: `id`, `created_at`, `user_id`, `user_name` (null for unknown or system; resolved through `identity.member_names`, "Unknown user" in the UI), `entity_type`, `entity_id`, `action`, `metadata` (already allowlisted at write time; the response model passes only `SAFE_METADATA_KEYS` again, defence in depth). No change to what is written |
| D3 | Audit UI | Page `/audit` with filters and a table (When, Who, What, Object, Details). "What" is plain words: `entity_type` and `action` humanised (`estimate` + `approved` = "Estimate approved"; unknown codes shown as the raw code). Details are `key: value` text, never HTML. The Audit nav link shows only for admin and project manager |
| D4 | Plans | Table `plans` (`code` primary key, `name`, `max_tenders`, `max_uploads_per_month`, `max_storage_mb`, `max_exports_per_month`, `max_members`; all positive integers) seeded by the migration with `demo` (25 tenders, 200 uploads a month, 1024 MB, 200 exports a month, 10 members) and `starter` (3, 10, 50, 20, 3). Table `organisation_plans` (`organisation_id` primary key, `plan_code`, `changed_by`, `changed_at`; composite FK to memberships for `changed_by`, F3). No row means `demo`. **(my call)** Two plans are enough to show enforcement; `demo` is the default so the marking demo never hits a limit by accident |
| D5 | What is counted | Computed live, never stored as counters, so they cannot drift: active (non-archived) tenders; document versions uploaded in the current UTC calendar month; total bytes of the organisation's document versions (rounded up to MB for display); exports created in the current month; active memberships. Each count is a `count_*` function in the owning module's `public.py`; the `billing` module never reads another module's tables |
| D6 | Enforcement points | In the API layer, before the creating service call, in the same transaction: `POST /tenders`, document upload and new version (incoming size counts toward storage), `POST /tenders/{id}/exports`, `POST /members` (and reactivating a member). Breaching raises `LimitExceeded` (403 `limit_exceeded`, existing mapping) with `"{Resource} limit reached on the {plan} plan ({used} of {limit})."`. Archiving a tender frees a tender slot. Reads, edits and deletes are never blocked by a limit |
| D7 | Race safety | The check takes `pg_advisory_xact_lock` keyed on a stable hash of `(organisation_id, resource)` before counting, so two concurrent creates for the last slot serialise and exactly one succeeds. A test with two threads proves it. The lock is released at commit or rollback |
| D8 | Usage API | `GET /api/v1/usage` (`READ`): plan code and name, and per resource `{used, limit, period}` (`period` is `current` for tenders, storage and members, `month` for uploads and exports). `PUT /api/v1/usage/plan` body `{plan_code}` (`MANAGE_MEMBERS`, so admin only; 404 for an unknown code, 422 shape) switches plan and records an audit event (`entity_type` `organisation`, `action` `plan_changed`, metadata `old_status`/`new_status` carrying the codes; no new metadata key). Switching to a smaller plan never deletes anything: the organisation is simply over the limit until it archives or waits for the month |
| D9 | Usage UI | Page `/settings/usage` for everyone with a bar per resource (text values too, not colour alone), "month" labels, and for admins a plan switch with plain wording: "This is a demo plan switch. No payment is taken." A refused action shows the server message in the existing error surface |
| D10 | Status endpoint | `GET /api/v1/health/status`, no login, per-IP rate limit (30 per minute): `{api: "ok", database: "ok"\|"down", model: "ok"\|"down"\|"not_configured"}`. Model check: GET `{LLM_BASE_URL}/api/tags` with a 2 s timeout when `LLM_PROVIDER` is `ollama`, result cached 10 s. No version, host, or model name in the response. Page `/status` renders it and refreshes every 15 s |
| D11 | Ops scripts language | PowerShell 7 scripts under `scripts/ops/` (the owner's machine is Windows), with the decision logic that can be unit-tested kept out of PowerShell: `scripts/ops_preflight.py` (standard library only) validates an env mapping and is tested by pytest. **(my call)** |
| D12 | Preflight rules | Errors: `SECRET_KEY` missing, `change-me`, or shorter than 32 characters; `POSTGRES_PASSWORD` still `intel` when `-Tunnel` is requested; with a tunnel, `ENVIRONMENT` not `production` or `COOKIE_SECURE` not `true`; `LLM_ALLOW_HOSTED=true` with a tunnel (a hosted model plus a public link plus real data is the combination the PRD forbids without an assessment) is a warning that needs `-AcceptHostedLlm`. Without a tunnel the secret and cookie rules are warnings |
| D13 | Backup layout | `backups/<UTC yyyyMMddTHHmmssZ>/` (git-ignored) with `db.dump` (`pg_dump -Fc` run inside the `db` container), `files.tar.gz` (the `files` volume archived by a throwaway container mounting it read-only), `manifest.json`: `created_at`, `git_commit`, `alembic_head`, `db_sha256`, `files_sha256`, `file_count`, `table_counts` (every public table), `tool_versions`. The script fails, and deletes the partial directory, if any part fails; an empty files volume is recorded as `file_count: 0`, not skipped |
| D14 | Restore | `restore.ps1 -Backup <dir> -Verify`: checks checksums against the manifest, restores the dump into a scratch database `inteltps_verify` inside the running `db` container and the archive into a scratch temp directory, compares table counts and file count with the manifest, drops the scratch database, removes the scratch directory, never writes to the live database or volume. `-Apply` additionally needs `-Project <name>` that is **not** the live project name unless `-IKnowThisReplacesLiveData` is also given; it stops `api` and `worker`, recreates the database, restores, extracts files into the `files` volume, runs `alembic upgrade head`, restarts, and waits for health. **(my call)** The gate runs `-Apply` against a second Compose project (`inteltps_gate`, Caddy on 8081 through `docker-compose.restore-test.yml`) so live data is never at risk |
| D15 | Tunnel | `tunnel.ps1` requires `cloudflared` on PATH (else exit 2 with the install hint), runs preflight with the tunnel rules, starts a quick tunnel to `http://127.0.0.1:8080` as a hidden background process, captures the `https://*.trycloudflare.com` URL from its log within 30 s, checks `/api/v1/health` through it (the `Secure` cookie flag is guaranteed by the preflight rule and the API's refusal to start with `COOKIE_SECURE=false` outside development, not re-tested here), writes `.demo/tunnel-url.txt` and `.demo/cloudflared.pid`. `-Stop` kills the recorded process. Named tunnels and Cloudflare Access are documented, not scripted |
| D16 | Start-demo | `start-demo.ps1 [-Tunnel] [-SkipModel] [-Stop]`: preflight, `docker info` check, Ollama `/api/tags` includes `LLM_MODEL` (else the exact `ollama pull` command), preload with `keep_alive` of 30 minutes, `docker compose up -d --build`, poll `/api/v1/health/status` until `database` is `ok` (max 180 s), optional tunnel, print URLs and the marking-window checklist from the PRD (power, sleep, updates, model loaded, URL posted, recording backup). `-Stop` runs `docker compose down` (volumes kept) and stops the tunnel |
| D17 | No new permission, no new dependency | Audit uses `VIEW_AUDIT`, usage reads use `READ`, plan switch uses `MANAGE_MEMBERS`. Backend: no new package. Frontend: none |

## 4. Boundaries

- `audit` gains `repo.py` (organisation-scoped read with keyset paging), a read service and schemas; it still imports no module.
- `billing` (today an empty stub) holds `plans`, `organisation_plans`, the limit service and `GET /usage` DTOs. It imports only `kernel`, `db` and `audit`; a new import-linter contract forbids every other module. The counts are passed in by the router, which is the only place that knows the modules.
- Routers: new `audit.py`, `usage.py`; `health.py` is not created, the status route lives in `main.py` beside the existing health routes.
- New migration `0008_plans_usage.py` (tables, seed rows, `organisation_plans` is created lazily on first plan switch).
- F1 sweep: audit and usage routes take no ids, so they are covered by `test_f1_lists_never_mix_organisations`, which gets the audit list added.

## 5. Risks

| Risk | Handling |
|---|---|
| Advisory-lock key collisions | Collisions only serialise two unrelated requests briefly; no correctness impact |
| A restore script that destroys data | `-Apply` refuses the live project name without an explicit flag; gate uses a second project |
| `cloudflared` not installed on the build machine | Reported "not run"; scripts still unit-checked by parse test |
| Quick tunnel URL changes each start | `tunnel-url.txt` and the start-demo summary always show the current one |
| Limits counted live cost a query per create | Five indexed counts per create; negligible at this scale |
